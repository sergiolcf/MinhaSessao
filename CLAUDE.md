# MinhaSessao - Diretrizes do Projeto

## Visão Geral
Sistema de gestão de sessões de psicologia para Psicólogos e Pacientes.
Solução: SLCF_MinhaSessao.sln
Tech Stack: .NET 8 MVC, Entity Framework Core, PostgreSQL (Neon.tech), Bootstrap 5.

## Paleta de Cores & Layout
- Fundo Principal: Cinza Claro (#F8F9FA)
- Texto / Elementos Primários: Grafite (#2B2D42)
- Destaques / Botões de Ação: Laranja (#FF6B35)
- Layout: Limpo, acolhedor. Autenticação (Login/Cadastro) usa páginas dedicadas (`_LayoutAuth`), não modais; modais Bootstrap continuam usados dentro do Dashboard (ex.: cadastro de paciente, anotações).

## Comandos Principais
- Compilar Solução: dotnet build SLCF_MinhaSessao.sln
- Rodar localmente: dotnet run --project MinhaSessao.csproj
- Migrações EF Core: dotnet ef database update --project MinhaSessao.csproj

## Regras de Código
- Sempre mantenha os botões de confirmação/ação no canto inferior DIREITO dos modais.
- Um único formulário de login para ambos os perfis (identificação via DB) — hoje é a página `/Account/Login`, não mais um modal.
- Código e comentários em Português (PT-BR).
- Sempre validar alterações compilando a solução antes de finalizar tarefas.
- Toda action que lê/grava dados vinculados a um Profissional (Pacientes, Anotações, etc.) deve usar `[Authorize(Roles = AutenticacaoService.PapelProfissional)]` e obter o Id do profissional logado via `User.ObterProfissionalId()`; toda action exclusiva do Paciente usa `[Authorize(Roles = AutenticacaoService.PapelPaciente)]` e `User.ObterPacienteId()` — nunca confiar em um Id vindo de querystring, rota ou corpo da requisição para autorização.
- Operações de CRUD dentro do Dashboard (criar/editar/excluir/paginar/buscar) devem ser feitas via Fetch API (AJAX), sem recarregar a página inteira.

## Segurança & Dependências
- NUNCA instale pacotes NuGet, bibliotecas externas ou serviços de terceiros sem solicitar autorização prévia ao usuário.
- O projeto DEVE utilizar exclusivamente tecnologias e bibliotecas 100% gratuitas e open-source (sem custos de licença ou planos pagos).

## Arquitetura Implementada
Esta seção descreve o estado atual do projeto por módulo/domínio (não por card). Ao implementar um novo card que altera um módulo existente, atualize a seção correspondente em vez de adicionar uma seção nova.

### Estrutura de Models e Projeto
- Namespace raiz do projeto é `MinhaSessao` (não `SLCF_MinhaSessao` — este é só o nome do arquivo `.sln`).
- `Models/Entities/*` — entidades mapeadas pelo EF Core (`Id` como `Guid`, gerado via `Guid.NewGuid()`).
- `Models/ViewModels/*` — models de formulário/exibição, um por finalidade (criação, edição, listagem, detalhes).
- `Services/*` — lógica de domínio reutilizável (ex.: `AutenticacaoService`).
- `Extensions/*` — extension methods auxiliares (ex.: `ClaimsPrincipalExtensions`).
- `Helpers/*` — `ValidationAttribute` customizados de DataAnnotations reutilizáveis entre ViewModels (`MaiorDeIdadeAttribute`, `CpfValidoAttribute`, `ArquivoValidoAttribute`); os dois primeiros também implementam `IClientModelValidator` para ter validação client-side (ver "Cadastro (Profissional e Paciente)").
- Persistência via EF Core + PostgreSQL (`Npgsql.EntityFrameworkCore.PostgreSQL`, hospedado no Neon.tech), `Data/ApplicationDbContext.cs`. A connection string (`ConnectionStrings:DefaultConnection`) **nunca** fica em texto puro no repositório: `appsettings.json` mantém a chave vazia (`""`) só para documentar o nome esperado; o valor real vem de `dotnet user-secrets` em desenvolvimento local (`dotnet user-secrets set "ConnectionStrings:DefaultConnection" "..."`, guardado fora do repo) e da variável de ambiente `ConnectionStrings__DefaultConnection` no Render em produção (o `__` mapeia para `:` na configuração do ASP.NET Core).
- **`ApplicationDbContext.OnModelCreating` força `DateTimeKind.Utc` em todo `DateTime`/`DateTime?` do model** (via `ValueConverter` aplicado em loop sobre `modelBuilder.Model.GetEntityTypes()`, não campo a campo) — o Postgres mapeia `DateTime` como `timestamp with time zone`, que rejeita `Kind=Unspecified`/`Local` no `SaveChanges` (`System.ArgumentException: Cannot write DateTime with Kind=Unspecified...`); isso não existia no SQLite (não valida `Kind`) e pegou o cadastro de Paciente de surpresa (`DataNascimento` chegando `Unspecified` de um `<input type="date">`) logo após a migração para Postgres. Qualquer novo campo `DateTime` criado no futuro já herda essa conversão automaticamente, sem precisar lembrar de tratar `Kind` no controller.
- `Program.cs` roda `context.Database.Migrate()` logo após `builder.Build()` (dentro de um `try/catch` que só loga o erro, sem derrubar a aplicação) — aplica automaticamente as migrations pendentes e cria o schema no Postgres se ainda não existir, tanto local quanto no Render, sem precisar rodar `dotnet ef database update` manualmente a cada deploy.

### Autenticação (Cookie + Senha, Profissional e Paciente)
- Autenticação real por Cookie (`Program.cs`: `AddAuthentication().AddCookie()`, `LoginPath = /Account/Login`, expira em 7 dias com sliding expiration).
- Senha nunca é armazenada em texto puro: hash via `PasswordHasher<Profissional>`/`PasswordHasher<Paciente>` (`Microsoft.AspNetCore.Identity`, já incluso no SDK `Microsoft.NET.Sdk.Web`, sem pacote NuGet adicional).
- `Services/AutenticacaoService.cs` centraliza hash/verificação de senha (`HashSenha`/`VerificarSenha` para Profissional, `HashSenhaPaciente`/`VerificarSenhaPaciente` para Paciente) e a autenticação (`AutenticarProfissionalAsync`/`AutenticarPacienteAsync`, montam os Claims e chamam `SignInAsync`). Ambos os métodos de autenticação adicionam um Claim de papel (`ClaimTypes.Role`) com o valor de `AutenticacaoService.PapelProfissional` ou `PapelPaciente` — é isso que permite `[Authorize(Roles = "...")]` diferenciar as rotas de cada perfil.
- `Extensions/ClaimsPrincipalExtensions.cs`: `ObterProfissionalId()`/`ObterPacienteId()` extraem o Id do usuário logado a partir dos Claims — é assim que toda controller descobre "quem está logado" (cada uma só é chamada dentro de controllers já restritas ao papel correspondente).
- `Controllers/AccountController.cs`: `Login` (GET/POST) é o único formulário para os dois perfis — normaliza o e-mail com `.Trim().ToLower()`, procura primeiro em `Profissionais` e depois em `Pacientes`, autentica com o método correspondente e redireciona para `Dashboard` (Profissional) ou `PainelPaciente` (Paciente). `LoginSimuladoTeste` (atalho de desenvolvimento, loga automaticamente o primeiro profissional do banco) e `LoginSimuladoPacienteTeste` (mesmo espírito, mas pro perfil Paciente) continuam existindo nas actions; os botões "Entrar com Conta de Teste" em `Views/Account/Login.cshtml` só aparecem quando a configuração `ExibirLoginContaTeste` é `true` (`Configuration.GetValue<bool>("ExibirLoginContaTeste")`, via `@inject IConfiguration Configuration` na própria View). **Essa flag é independente de `ASPNETCORE_ENVIRONMENT` de propósito** — usar `Env.IsDevelopment()` (versão antiga) juntava dois conceitos diferentes, e qualquer serviço hospedado no Render com `ASPNETCORE_ENVIRONMENT=Development` por qualquer motivo (ex.: Homolog, só pra ver stack trace de erro) acabava expondo esse botão de teste sem querer. `appsettings.json` define o default `"ExibirLoginContaTeste": false` — vale pra **qualquer** ambiente hospedado (Develop/Homolog/Produção no Render) que não sobrescreva explicitamente; `Properties/launchSettings.json` define `"ExibirLoginContaTeste": "true"` como variável de ambiente só do `dotnet run`/IIS Express **local** — esse arquivo nunca é lido por um serviço publicado no Render, então o botão continua aparecendo pro desenvolvedor local sem precisar mexer em nada no Render pra isso. Se algum dia for necessário habilitar esse botão num serviço hospedado específico, é uma variável de ambiente nova (`ExibirLoginContaTeste=true`) a ser configurada manualmente naquele serviço — nunca o `ASPNETCORE_ENVIRONMENT`. `Logout` (comum aos dois perfis).
- `LoginSimuladoPacienteTeste` procura o paciente "Sergio Teste" (`_context.Pacientes`, por `NomeCompleto`) e, se não existir, cria com dados fictícios (telefone/CPF/e-mail/data de nascimento normalizados, mesmo padrão de `PacientesController.Criar`) e senha temporária via `AutenticacaoService.GerarSenhaTemporaria`/`HashSenhaPaciente`; em qualquer um dos dois casos (paciente novo ou já existente) garante o vínculo ativo com o primeiro profissional cadastrado via `_vinculoService.CriarVinculo` (só cria se `PacientePertenceAoProfissionalAsync` retornar `false`) antes de autenticar e redirecionar pra `PainelPaciente`. Mesma mensagem de erro de `LoginSimuladoTeste` se não houver nenhum profissional cadastrado ainda.
- Views: `Views/Account/Login.cshtml` e `Views/Account/Cadastro.cshtml`, ambas com `Views/Shared/_LayoutAuth.cshtml` (layout minimalista, não usa o `_Layout.cshtml` público nem os layouts de dashboard).
- Ainda não implementado: troca de senha obrigatória no primeiro login e recuperação de senha. O Paciente pode ganhar acesso tanto pelo cadastro feito pelo Profissional (senha temporária, ver "Pacientes" abaixo) quanto por autocadastro próprio (ver "Cadastro (Profissional e Paciente)" abaixo).

### Cadastro (Profissional e Paciente)
- Tela única `Views/Account/Cadastro.cshtml` (`_LayoutAuth`), com abas Bootstrap ("Sou Profissional" / "Sou Paciente") — substituiu o antigo modal de cadastro do Profissional na landing page e a rota solta `/Paciente/Cadastrar`. Cada aba é um `<form>` independente que posta para uma action diferente do `AccountController`; os campos usam nomes simples (`NomeCompleto`, `Email`, `Senha`...), sem prefixo `Model.Profissional.X`/`Model.Paciente.X`, porque cada action recebe seu próprio ViewModel (`ProfissionalViewModel`/`PacienteCadastroViewModel`) direto como parâmetro — os campos de cada aba vêm de um `<partial>` próprio (`_CamposCadastroProfissional.cshtml`/`_CamposCadastroPaciente.cshtml`) com `@model` do tipo específico, exatamente para gerar esses nomes sem prefixo.
- `Models/ViewModels/CadastroViewModel.cs` só existe para renderizar a tela (`PerfilAtivo` + os dois sub-ViewModels vazios ou repopulados após erro) — nunca é o tipo postado por um form.
- `Controllers/AccountController.cs`:
  - `[HttpGet] Cadastro(string? perfil)` — monta a tela; `PerfilAtivo` vem da querystring (`?perfil=paciente`), default `"profissional"`.
  - `[HttpPost] CadastroProfissional(ProfissionalViewModel model)` — mesma lógica que existia em `ProfissionalController.Criar` (upload de foto opcional para `wwwroot/uploads/profissionais/`, hash da senha, autologin), mas retornando `View`/`RedirectToAction` em vez de `Json` (form MVC tradicional, mesmo padrão do `Login`). Sucesso → `RedirectToAction("Index", "Dashboard")`, direto, sem modal de sucesso.
  - `[HttpPost] CadastroPaciente(PacienteCadastroViewModel model)` — mesma lógica que existia em `PacienteController.Cadastrar` (checagem de e-mail duplicado, hash da senha, autologin). Sucesso → `RedirectToAction("Index", "PainelPaciente")`. **Não cria nenhum `VinculoPacienteProfissional`** — vínculo continua sendo criado só pelo Profissional (ver "Pacientes"/"Vínculo Paciente-Profissional"). Antes de gravar, `Telefone` é normalizado inline (`new string(model.Telefone.Where(char.IsDigit).ToArray())`, mesmo espírito de `CpfUtil.Normalizar` mas sem reaproveitar essa classe — o nome é específico de CPF) — `Cpf` já era normalizado via `CpfUtil.Normalizar`. Assim, ambos os campos são salvos só com dígitos, independente da máscara aplicada no front-end.
  - Em erro (validação ou e-mail duplicado), cada action re-renderiza `View("Cadastro", ...)` com `PerfilAtivo` na aba correta e os dados já digitados preservados.
- `wwwroot/js/cadastro.js` — contador de caracteres da Apresentação do Profissional (migrado do antigo `site.js`); as máscaras de `#Cpf`/`#Telefone` (aba Paciente) e `#RegistroCRP`/`#Telefone` (aba Profissional, `00/000000` e fixo/celular dinâmico) — vanilla JS puro (sem lib nova), função `aplicarMascara` reformata o `value` do input nos eventos `input`/`blur`/`change` (não só `input`: alguns fluxos de autopreenchimento do navegador podem preencher o campo sem disparar um `input` "de verdade", então a máscara ficava sem aplicar — reportado em teste manual do usuário) e também reformata uma vez de cara caso o campo já chegue preenchido. **Toda busca de campo é escopada a `#tab-paciente`/`#tab-profissional`** (`querySelector`, nunca `getElementById` puro) — `Telefone` existe nos dois formulários da mesma página (`Cadastro.cshtml` renderiza as duas abas no DOM, só uma fica visível), então `getElementById("Telefone")` sempre pegava o primeiro do documento (Profissional) e deixava o outro sem máscara; **e** os adaptadores do jQuery Validate Unobtrusive (`maiordeidade`/`cpfvalido`, registrados fora do `DOMContentLoaded` para rodar antes do unobtrusive escanear o formulário) que dão vida client-side aos `ValidationAttribute` customizados que implementam `IClientModelValidator` — sem isso, um `ValidationAttribute` customizado só é checado no POST (servidor), nunca ao digitar/perder foco, diferente de `[Required]`/`[RegularExpression]`/etc, que já têm suporte nativo do ASP.NET Core; `configurarValidacaoFoto()` faz uma checagem equivalente (tamanho/extensão) para o input de arquivo `#Foto`, fora do jQuery Validate (File API não tem adaptador unobtrusive pronto), limpando o input e escrevendo direto no `data-valmsg-for="Foto"` quando inválido; **e** `configurarToggleSenha()`, um botão próprio de mostrar/ocultar senha (`.ms-toggle-senha`, ícone `bi-eye`/`bi-eye-slash` dentro de um `input-group` ao lado de cada campo Senha/ConfirmarSenha, nos dois formulários) — existe porque o ícone nativo de revelar senha do navegador (Edge, alguns gerenciadores de senha) aparece de forma inconsistente entre campos/navegadores e não dá pra controlar via CSS/JS; o nativo do Edge é escondido via `::-ms-reveal`/`::-ms-clear` em `auth.css` para não duplicar com o nosso ícone.
- **Validação de `PacienteCadastroViewModel`** (autocadastro de Paciente, `Views/Account/_CamposCadastroPaciente.cshtml`): `NomeCompleto` exige `[StringLength(3, 100)]` + `[RegularExpression]` (só letras/acentos, com espaço — força nome e sobrenome); `Telefone` usa `[RegularExpression]` aceitando tanto o valor já mascarado pelo JS quanto dígitos puros (fallback caso o JS não rode), garantindo 10/11 dígitos; `Cpf` usa `[RegularExpression]` (formato/quantidade de dígitos) **e** `[CpfValido]` (`Helpers/CpfValidoAttribute.cs` — delega o cálculo pra `CpfUtil.EhValido`, ver "Pacientes" abaixo; rejeita também CPF com todos os dígitos iguais tipo `111.111.111-11`; um CPF só com formato correto mas dígito verificador errado, ex. `147.147.144-78`, passava batido antes dessa validação existir); `DataNascimento` usa `[MaiorDeIdade(18)]` (`Helpers/MaiorDeIdadeAttribute.cs` — calcula idade a partir de `DateTime.UtcNow.Date`, reutilizável em qualquer ViewModel com campo de data de nascimento); `Senha` exige `[MinLength(8)]` + `[RegularExpression]` (1 maiúscula, 1 número, 1 caractere especial). `MaiorDeIdadeAttribute` e `CpfValidoAttribute` implementam `IClientModelValidator` (gerando `data-val-maiordeidade`/`data-val-cpfvalido` nos inputs) justamente para terem validação ao vivo igual aos atributos nativos — ver `cadastro.js` acima. `Models/ViewModels/PacienteViewModel.cs` (cadastro de Paciente feito pelo Profissional, `PacientesController.Criar`) ganhou o mesmo `[CpfValido]` no CARD-34 (mantendo só `[Required]`, sem o `[RegularExpression]` de formato/máscara que o autocadastro tem).
- **Validação de `ProfissionalViewModel`** (`Views/Account/_CamposCadastroProfissional.cshtml`): `NomeCompleto` exige `[StringLength(3, 100)]` + `[RegularExpression]` (nome e sobrenome, mesma regra do Paciente); `RegistroCRP` usa `[RegularExpression]` no formato `00/000000` (2 dígitos + `/` + 6 dígitos); `Telefone` usa a mesma `[RegularExpression]` fixo/celular do Paciente; `Senha` exige `[MinLength(8)]` + `[RegularExpression]` (1 maiúscula, 1 número, 1 caractere especial — antes só pedia 6 caracteres, sem mais regra nenhuma); `Apresentacao` passou de opcional (`string?`, só `[StringLength(500)]`) para obrigatória (`string`, `[Required]` + `[StringLength(500, MinimumLength = 30)]`) — só afeta o autocadastro, `AtualizarPerfilProfissionalViewModel` (tela Configurações) é um ViewModel separado e continua sem exigir tamanho mínimo; `Foto` (`IFormFile?`, continua opcional) ganhou `[ArquivoValido]` (`Helpers/ArquivoValidoAttribute.cs` — máximo 2MB, extensões `.jpg`/`.jpeg`/`.png`; sobrescreve o overload `IsValid(object, ValidationContext)` em vez de mutar `ErrorMessage` em `IsValid(object)`, para não compartilhar estado entre requisições concorrentes na mesma instância cacheada do atributo — mensagem final distingue "tamanho" de "extensão inválida", por isso não implementa `IClientModelValidator`/`data-val-*`; o equivalente client-side é o `configurarValidacaoFoto()` do `cadastro.js`, feito com a File API direto, não via jQuery Validate).

### Configurações (Profissional)
- Tela única em `Views/Dashboard/Configuracoes.cshtml` (layout `_LayoutDashboard`), com abas Bootstrap ("Perfil Profissional" / "Preferências da Clínica" / "Segurança"), mesmo padrão visual/AJAX da tela `Configuracoes` do Paciente (Fetch API por form, feedback em Bootstrap Toast, sem reload de página).
- Aba "Perfil Profissional": Nome/CRP/Telefone/Abordagem/Biografia começam `readonly`, com botão "Editar Perfil" que libera esses campos e troca pelos botões "Salvar Alterações"/"Cancelar" (`wwwroot/js/dashboard-configuracoes.js`, mesmo padrão de `wwwroot/js/painel-configuracoes.js`); "Cancelar" restaura os valores originais e volta pro modo leitura, e um salvamento bem-sucedido também volta pro modo leitura. O campo E-mail é **sempre** `readonly` (nunca entra em modo edição, mas continua sendo enviado no POST — só `readonly`, não `disabled`, porque um campo `disabled` não é incluído no `FormData` e quebraria a validação `[Required]` do e-mail no servidor) e mostra abaixo um texto explicando que ele é o login de acesso.
- `Models/Entities/Profissional.cs` ganhou `AbordagemEspecialidades` (string?, até 200 caracteres — distinto de `Apresentacao`, que continua sendo a biografia livre) e as preferências da clínica `DuracaoPadraoSessaoMinutos` (int, default 50) e `ValorPadraoConsulta` (decimal) — migration `AdicionaConfiguracoesProfissional`. Registros criados antes dessa migration ficaram com `DuracaoPadraoSessaoMinutos = 0`; `DashboardController.Configuracoes` corrige isso na leitura (exibe 50 se o valor salvo for 0), sem precisar tocar no banco.
- `Models/ViewModels/ConfiguracoesProfissionalViewModel.cs` (dados pra renderizar a tela), `AtualizarPerfilProfissionalViewModel.cs`, `AtualizarPreferenciasProfissionalViewModel.cs` e `AlterarSenhaProfissionalViewModel.cs` — um ViewModel por form, cada um postado direto como parâmetro (mesmo padrão do Cadastro/Configurações do Paciente).
- `DashboardController` (`[Authorize(Roles = AutenticacaoService.PapelProfissional)]`, já aplicado à classe):
  - `Configuracoes()` (GET) — carrega o próprio Profissional logado via `User.ObterProfissionalId()`.
  - `AtualizarPerfil(AtualizarPerfilProfissionalViewModel)` (POST, JSON) — atualiza Nome/E-mail/Telefone/CRP/Abordagem/Apresentação; revalida duplicidade de e-mail contra outros Profissionais antes de salvar.

### Pacientes
- `Controllers/PacientesController.cs`: `Index` (lista os pacientes vinculados ao profissional logado), `Detalhes` (ficha do paciente), `VerificarPacienteExistente`, `Vincular`, `Criar`, `GerarNovaSenha`.
- Toda consulta/gravação revalida a posse via `VinculoService` (ver seção "Vínculo Paciente-Profissional" abaixo) — **nunca** compara um `ProfissionalId` direto na entidade `Paciente` (ela não tem mais esse campo).
- **`Index` — paginação (10 por página) + busca por nome/CPF**, mesmo espírito de `SessoesController`, mas com uma diferença importante: a base de dados (`_vinculoService.ObterPacientesAtivosAsync`) já carrega todos os pacientes ativos do profissional pra memória, então `PacientesController.ObterPaginaPacientesAsync` (privado, reaproveitado por `Index` e `BuscarPacientes`) filtra/ordena/pagina em LINQ-to-Objects, não numa nova consulta ao banco — filtro por nome (`Contains` case-insensitive) ou CPF normalizado (`CpfUtil.Normalizar`, mesma checagem de `BuscarPacientesFiltro` em `SessoesController`). `BuscarPacientes(int pagina, string? termo)` (GET, JSON) é o endpoint AJAX; `Index()` só busca a página 1 sem filtro. Na View, `#filtroPacienteBusca` (mesmo padrão visual `.ms-anotacao-toolbar`/`.ms-anotacao-search` das Anotações Confidenciais) dispara a busca com debounce de 400ms em `wwwroot/js/pacientes.js`, sempre reiniciando na página 1.
  - **Altura do scroll calculada em JS, não em CSS fixo**: a linha de paciente tem duas informações empilhadas na coluna Contato (WhatsApp + e-mail), então sua altura real não bate com o `max-height` fixo usado em Sessões (`.ms-dash-table-scroll`). `.ms-dash-table-scroll-pacientes` só define `overflow-y: auto`; `ajustarAlturaTabelaPacientes()` (`pacientes.js`) mede `thead` + uma linha `tr[data-paciente-id]` já renderizada via `getBoundingClientRect()` e aplica `maxHeight = alturaThead + alturaLinha × 4` como estilo inline — chamada no carregamento inicial, depois de cada `carregarPacientes()` (mantendo o último valor calculado se não houver linha pra medir, ex. busca sem resultado) e num `resize` da janela (debounce de 200ms).
  - Cada linha vem da partial `Views/Pacientes/_LinhaPaciente.cshtml` (espelhada em `construirLinhaPaciente` no JS, mesmo padrão de `_LinhaSessao.cshtml`/`construirLinhaSessao`).
- **Fluxo "Novo Paciente"** (modal `#modalCadastroPaciente` em `Views/Pacientes/Index.cshtml`, controlado por `wwwroot/js/pacientes.js`), pra não duplicar paciente que já existe — **o CPF é o identificador usado pra buscar/evitar duplicidade** (o e-mail é só um campo cadastral comum, não é mais usado nessa checagem):
  0. Etapa "Precisa de um responsável?" (Sim/Não) — **primeira etapa do modal**, adicionada no CARD-35 pra atender **Paciente com Responsável** (menores de idade). A resposta fica só em memória no JS (`necessitaResponsavel`), reiniciada pra `false` toda vez que o modal reabre (`show.bs.modal`). Responder "Não" segue o fluxo de sempre (item 1 abaixo, inalterado). Responder "Sim" habilita o campo extra "CPF do Responsável" na etapa seguinte e o campo "CPF do Paciente" passa a ser opcional.
  1. Etapa "Verificar CPF" — campo de CPF do Paciente (com máscara `000.000.000-00` aplicada em JS puro, sem lib nova; obrigatório só quando não há Responsável) e, quando há Responsável, também um campo "CPF do Responsável" (obrigatório). `[HttpGet] VerificarPacienteExistente(cpf, cpfResponsavel)` valida o dígito verificador com `CpfUtil.EhValido` **antes** de consultar o banco (CARD-34 — CPF com formato certo mas dígito inválido nem chega a bater no banco): se `cpf` foi informado, busca por ele (`BuscarPacientePorCpfAsync`, mesmo comportamento de sempre); se `cpf` veio vazio e há `cpfResponsavel` (paciente menor sem CPF próprio, CARD-35), busca em `Pacientes.CpfResponsavel` — como um mesmo responsável pode ter mais de um filho cadastrado, se encontrar **mais de um** paciente, não escolhe um automaticamente: retorna `{ existe: true, cpfValido: true, multiplos: true, pacientes: [{ id, nomeCompleto, iniciais }, ...] }`. `wwwroot/js/pacientes.js` (`verificarCpf()`) checa `resultado.cpfValido` antes de olhar `resultado.existe`/`resultado.multiplos`, exibindo "CPF inválido..."/"CPF do responsável inválido..." quando falso.
  1b. Se `multiplos: true` → etapa "Escolher paciente" (`renderizarListaPacientesEncontrados`): lista os pacientes encontrados como botões ("é um desses?"); clicar num deles leva pra etapa "Paciente encontrado" (item 2, reaproveitando o mesmo fluxo de vincular); um link "Nenhum desses, cadastrar novo paciente" leva direto pra etapa "Cadastro completo" (item 3) com o CPF do Responsável já preenchido e o CPF do Paciente em branco.
  2. Se `existe: true` (e não `multiplos`) → etapa "Paciente encontrado" (mostra iniciais/nome, sem reexibir nem sobrescrever os dados dele). Botão "Vincular este paciente" chama `[HttpPost] Vincular(pacienteId)`, que confere se já está vinculado (erro "Este paciente já está na sua lista.") e senão chama `VinculoService.CriarVinculo` — **não** gera senha nova nem mexe no cadastro do paciente.
  3. Se `existe: false` → etapa "Cadastro completo" (`formCadastroPaciente`). O campo CPF do Paciente vem preenchido e `readonly` (com link "trocar CPF") só quando foi de fato informado na etapa 1; se ficou em branco (paciente menor sem CPF próprio), o campo fica editável e sem o asterisco de obrigatório (`irParaCadastroCompleto` em `pacientes.js` decide isso). Quando há Responsável, a seção "Dados do Responsável" (`#cadastroResponsavelFields`) aparece com Nome/Telefone do Responsável (obrigatórios) e o CPF do Responsável já preenchido/`readonly` (vindo da etapa 1); um campo oculto `NecessitaResponsavel` (`"true"`/`"false"`) acompanha o restante do formulário no POST pro `[HttpPost] Criar` de sempre.
  - `Criar` continua existindo exatamente como antes (gera senha temporária, cria o Vínculo), mas a checagem de duplicidade por CPF no envio final passou a ser só uma **rede de segurança contra condição de corrida**, e só roda quando `model.Cpf` foi informado (CARD-35 — CPF do paciente é opcional quando há Responsável, então essa checagem não faz sentido quando ele ficou em branco; a etapa de verificação pelo CPF do Responsável já cobre a duplicidade nesse caso) — não deveria ocorrer no fluxo normal (a tela já checou o CPF na etapa 1); se ocorrer, `Criar` **não cadastra** e retorna erro pedindo pra verificar de novo (sem vincular automaticamente).
  - O modal sempre volta pra etapa 0 ao reabrir (`show.bs.modal` reseta tudo, inclusive `necessitaResponsavel`).
  - `Models/ViewModels/CpfUtil.cs` centraliza a normalização de CPF (remove tudo que não for dígito) — usado tanto por `PacientesController` quanto por `AccountController.CadastroPaciente`, pra garantir que o CPF é sempre armazenado só com dígitos, e as buscas funcionam independente de como foi digitado. **`CpfUtil.EhValido(string?)` (CARD-34)** centraliza também a validação do dígito verificador (algoritmo oficial, módulo 11, rejeita dígitos todos iguais) — `Helpers/CpfValidoAttribute.cs` delega pra esse método em vez de duplicar o cálculo (o algoritmo em si morava antes dentro do próprio atributo).
  - **Paciente com Responsável (CARD-35)**: `Models/Entities/Paciente.cs` ganhou `NecessitaResponsavel` (bool, default `false`), `NomeResponsavel`/`TelefoneResponsavel`/`CpfResponsavel`/`ProfissaoResponsavel` (todos `string?`, este último opcional — migrations `AdicionaResponsavelPaciente` e `AdicionaProfissaoResponsavelPaciente`). O CPF do paciente (`PacienteViewModel.Cpf`) deixou de ser `[Required]`: `PacienteViewModel` agora implementa `IValidatableObject` pra exigir Nome/Telefone/CPF do Responsável quando `NecessitaResponsavel` é `true` (a Profissão do Responsável nunca é obrigatória, mesmo padrão da Profissão do próprio paciente), ou o CPF do próprio paciente quando é `false` — a mesma regra condicional vale só pro cadastro feito pelo Profissional; `PacienteCadastroViewModel` (autocadastro do próprio paciente) continua com CPF `[Required]` sempre, sem esse conceito de Responsável. Na tela (`#cadastroResponsavelFields`), os campos de Responsável (Nome/Telefone/CPF/Profissão) ficam dentro de um contêiner com fundo destacado (`.ms-secao-responsavel`, `dashboard.css` — mesmo cinza claro `var(--ms-bg)`/`#F8F9FA` usado em outras seções, ex.: hover da Agenda), separando visualmente esses dados dos do próprio paciente.
- Acesso do paciente: ao cadastrar do zero, `Criar` gera uma senha temporária aleatória (`AutenticacaoService.GerarSenhaTemporaria`), salva só o hash (`HashSenhaPaciente`) e retorna o texto puro **uma única vez** no JSON de sucesso. O front-end (`wwwroot/js/pacientes.js` + modal compartilhada `#modalSenhaTemporaria` em `_LayoutDashboard.cshtml`, via `window.exibirSenhaTemporaria`) exibe essa senha com um botão de copiar (`navigator.clipboard`) — ela nunca é armazenada em texto puro nem pode ser recuperada depois.

Não existe fluxo de "recuperar" a senha antiga — só resetar.
- O paciente já consegue logar com essa senha em `/Account/Login` (login continua sendo por e-mail, ver seção "Autenticação" acima) e cai no seu próprio painel — ver "Painel do Paciente" abaixo. Exclusão usa `window.confirm` (mesmo padrão de `anotacoes.js`).
- **Objetivos Trabalhados não é mais salvo separado** — antes existia uma action/botão "Salvar Objetivos" próprios (`AtualizarObjetivosSessao`) que foi removida: salvar uma anotação já salva os objetivos marcados nela, no mesmo request.
- **Estado "visualização" (CARD-31)**: além de "vazio"/"compondo" (novo/editando), o painel esquerdo (`composeEl`) tem um terceiro estado só de leitura — `visualizandoId` (variável separada de `composing`/`editId`, propositalmente ignorada por `temRascunho()`: trocar de anotação visualizada, ou começar uma nova, não deve disparar aviso de "descartar rascunho", já que não é um rascunho editável). `renderVisualizacao(anotacao)` mostra Título (`.ms-anotacao-sessao-compose-titulo`), os Objetivos Trabalhados como chips somente leitura (`.ms-objetivo-chip`, mesmo componente da lista à direita — não é o checklist editável de `renderObjetivosHtml`) e o Conteúdo com quebras de linha preservadas (`escaparHtml` primeiro, só depois troca `\n` por `<br>`, pra não reabrir brecha de HTML injection através do próprio caractere de quebra de linha), com um botão "Editar" que chama `abrirEdicao(anotacao.id)` (fluxo real de edição, reaproveitado). Esse estado é alcançado de duas formas: (1) automaticamente, se a URL trouxer `?anotacaoId=...` (ver abaixo); (2) pelo botão "Visualizar" (`bi-eye`, `data-visualizar-anotacao`, antes do de Editar) de cada item da lista à direita — `abrirVisualizacao(id, forcar)` ainda pede confirmação via `pedirDescarte` se houver rascunho não salvo em andamento (visualizar não é destrutivo, mas trocar o painel sem avisar perderia o que a pessoa estava digitando).
- **Deep link com `?anotacaoId=...` (CARD-31)**: chegando à tela a partir do link "Abrir sessão"/linha clicável da aba "Anotações Clínicas" da Ficha do Paciente (ver seção acima), a URL já traz esse parâmetro. `SessoesController.Sessao(Guid id)` não precisou de nenhuma mudança — não redireciona no caminho feliz, então a query string sobrevive até o browser renderizar a view. Em `sessao-detalhe.js`, `abrirAnotacaoDaUrlSeNecessario()` (chamada uma única vez, logo após a primeira `renderizarLista()` dentro de `carregarAnotacoes()`, guardada por `ms_anotacaoJaDestacada` pra não repetir em recargas subsequentes da lista após salvar/excluir) faz `scrollIntoView({behavior:"smooth", block:"center"})` + aplica a classe `.ms-anotacao-destacada` por 2,5s no item correspondente da lista à direita (`data-anotacao-id`, `dashboard.css`) **e** chama `renderVisualizacao` pra já abrir o conteúdo no painel esquerdo — não fica só no destaque da lista, evitando um clique extra do profissional.
- **Hierarquia de destaque dos títulos do card (CARD-31)**: `.ms-anotacao-sessao-compose-titulo` (título no painel principal, à esquerda — em qualquer um dos três estados: nova/editando/visualizando) é o texto de maior destaque da tela (`1.1rem`/`700`, é o conteúdo em foco); `.ms-anotacao-sessao-lista-titulo` ("Anotações desta sessão", cabeçalho da lista à direita) vem em segundo (`0.95rem`/`700`, peso forte compensando o tamanho menor da coluna); `.ms-anotacao-sessao-item-titulo` (título de cada item dentro da lista) é o menor dos três (`0.85rem`/`500`) — antes desse ajuste o item da lista não tinha `font-size` definido (herdava um valor maior que os outros dois), invertendo a hierarquia visual esperada.

- View 100% orientada a AJAX (sem SSR da lista, diferente do padrão usado em Anotações/Sessões — simplificação deliberada, mesmo espírito da Agenda V0): `Views/Pacientes/Detalhes.cshtml` só renderiza o container `#objetivosContainer`/`#listaObjetivos` vazio (com empty state) e a modal `#modalNovoObjetivo`; `wwwroot/js/plano-tratamento.js` (IIFE própria, sem interferir com `anotacoes.js`) chama `ListarObjetivos` assim que a página carrega e renderiza os cards.
- Card por objetivo: título + badge de status (`bg-info` Em Andamento, `bg-success` Atingido, `bg-warning text-dark` Pausado — o projeto usa Bootstrap 5.1, que não tem o utilitário `text-bg-*` do 5.3, por isso o `text-dark` manual pro contraste no amarelo —, `bg-secondary` Cancelado), progress bar Bootstrap nativa (`combinadosConcluidos`/`totalCombinados`), lista de combinados com checkbox (chama `AlternarCombinado` no `change`) e um `<select>` de status (chama `AtualizarStatusObjetivo` no `change`) — os dois recarregam a lista inteira do servidor após a chamada (fonte da verdade fica no backend, sem estado otimista complexo no JS).
- **Histórico de Sessões** (dentro do card, abaixo da lista de combinados), carregado sob demanda e paginado — não vem junto do `ListarObjetivos` inicial, pra não pesar a tela quando um objetivo acumula muitas sessões: `ObjetivoTerapeutico` ganhou a navegação `ICollection<SessaoObjetivo> SessoesObjetivo` (configurada em `ApplicationDbContext.OnModelCreating` via `WithMany(o => o.SessoesObjetivo)` no relacionamento `SessaoObjetivo`→`ObjetivoTerapeutico` já existente — mesma FK/coluna de antes, só nomeando a navegação inversa, por isso não precisou de migration nova). `PacientesController.ListarObjetivos` expõe só a contagem `totalSessoesVinculadas = o.SessoesObjetivo.Count` de cada objetivo; a lista de sessões em si vem de `ListarSessoesDoObjetivo(Guid objetivoId, int pagina = 1)` (GET, paginação fixa de 10, valida o dono comparando `ObjetivoTerapeutico.ProfissionalId` direto — mesmo padrão simplificado de `AtualizarStatusObjetivo`/`ExcluirObjetivo`, sem precisar do `VinculoService` porque o objetivo já guarda o `ProfissionalId` de quem criou —, retorna `{ success, sessoes: [{ sessaoId, codigo, dataHora, observacao }], paginaAtual, totalPaginas }` ordenado por `AnotacaoSessao.Sessao.DataHora` decrescente — `so.AnotacaoSessao!.Sessao!.*`, já que cada `SessaoObjetivo` vincula a uma `AnotacaoSessao`, não mais direto à `Sessao` (ver seção "Conteúdo Clínico da Sessão" acima); **nuance aceita**: se o profissional marcar o mesmo objetivo em mais de uma anotação da mesma sessão, essa sessão aparece mais de uma vez aqui — não há deduplicação. `sessaoId`/`codigo` alimentam o popup somente leitura descrito abaixo. Em `plano-tratamento.js`, `criarCardObjetivo` renderiza um link "Histórico de Sessões (N)" (`data-bs-toggle="collapse"`, mesmo padrão da "Evolução da Sessão" em `Pacientes/Detalhes.cshtml`) sobre uma `.collapse` vazia (`data-carregado="false"`); o listener `show.bs.collapse` em `listaObjetivos` (delegado, dispara na primeira expansão de cada card) chama `carregarHistoricoSessoes(collapseEl, 1)`, que busca a página e marca `data-carregado="true"` — expansões seguintes não buscam de novo. Um botão "Carregar mais" dentro da própria `.collapse` (escondido quando `paginaAtual >= totalPaginas`) busca a próxima página e faz *append* na lista (`insertAdjacentHTML("beforeend", ...)`), sem substituir os itens já carregados. Sem nenhuma sessão vinculada (`totalSessoesVinculadas === 0`), o card mostra só o texto "Nenhuma sessão registrada ainda" (sem link nem `.collapse`). Como `carregarObjetivos()` reconstrói todos os cards do zero a cada ação (criar/excluir objetivo, alternar combinado, mudar status), o histórico expandido sempre volta a fechado/não carregado depois de qualquer uma dessas ações — comportamento aceito, não é bug. Estilos `ms-objetivo-historico-*` em `dashboard.css`.
- **Popup "Visualizar Sessão" (somente leitura)**: cada item de "Histórico de Sessões" mostra `Codigo — Data` (ex.: `MS_1_SF — 11/09/2026`, em vez de só a data) como um botão (`.ms-objetivo-historico-data-link`, cor verde-sálvia, sem fundo) — clicar chama `abrirModalVisualizarSessao(sessaoId)` em `plano-tratamento.js`, que busca `/Sessoes/ObterSessao?id=...` (**mesmo endpoint** da modal de edição em Minhas Sessões, sem endpoint novo) e preenche o `#modalVisualizarSessao` (único, declarado uma vez no fim de `Views/Pacientes/Detalhes.cshtml`, reaproveitado por qualquer sessão clicada): Código/Data e Hora/Duração/Status (`row`/`col-3` do Bootstrap — não reaproveita `.ms-dash-info-grid` porque essa classe foi customizada num card anterior pra 8 campos em 4 colunas, não serve pra 4 campos lado a lado), objetivos vinculados (agregados de todas as anotações da sessão) como chips `.ms-objetivo-chip` e Anotações Clínicas — agora uma **lista** (`dados.anotacoes`, cada uma com título + conteúdo, já que a sessão pode ter várias) em vez de um texto único, renderizada em `#modalVisualizarSessaoAnotacoes` (`div`, não mais `<p>`); "Nenhuma anotação registrada." quando a lista vem vazia. Modal só com botão "Fechar" — sem nenhuma ação de editar/salvar (editar de fato é só pela tela dedicada `Sessoes/Sessao/{id}`).
- O envio da modal "Novo Objetivo" usa `FormData`/campos de formulário (nunca JSON) — é o que faz o `[ValidateAntiForgeryToken]` e o model binding do `List<string> Combinados` funcionarem (o MVC lê o token e monta a lista a partir de múltiplos campos `Combinados` com o mesmo nome; um `fetch` com `Content-Type: application/json` quebraria os dois).
- Estilos próprios `ms-objetivo-*`/`ms-combinado-*` em `dashboard.css`, reaproveitando `ms-dash-card`/`ms-dash-empty-state`/`ms-dash-page-header`/`ms-required`/`ms-alert-erro` já existentes.
- **`.ms-objetivos-grid-scroll` (CARD-33)** — wrapper com `max-height: 700px`/`overflow-y: auto` em volta do `.ms-objetivos-grid`, pra a lista de objetivos ganhar scroll interno em vez de esticar a página inteira quando há muitos. `max-height` fixo de propósito, não calculado via JS: diferente de uma tabela (uma "altura de linha" única, multiplicável por N), aqui os cards têm altura variável (depende da quantidade de combinados de cada objetivo), então não existe uma unidade única pra medir — usado nas 3 telas que têm `.ms-objetivos-grid` (esta, "Planos de Tratamento" do profissional e "Meus Planos de Tratamento"/"Meus Objetivos" do paciente, ambas abaixo).
- Fica para um card futuro: edição de título/descrição de um objetivo já criado (hoje só criação, mudança de status e exclusão pelo profissional). A necessidade de uma "tela de histórico/filtro caso o volume de objetivos por paciente cresça" citada aqui antes do CARD-33 foi endereçada, mas como uma tela **cross-paciente** separada (ver "Planos de Tratamento (Painel do Profissional)" abaixo), não como paginação dentro desta aba.

### Planos de Tratamento (Painel do Profissional)
- Tela nova (CARD-33), item próprio no menu lateral (`bi-bullseye`, entre "Minhas Sessões" e "Configurações") — mostra os Objetivos Terapêuticos de **todos** os pacientes do profissional numa lista só, com filtro por Paciente/Período (data de criação)/Status, complementando a aba "Plano de Tratamento" da Ficha do Paciente (que é por paciente).
- `Controllers/PlanosTratamentoController.cs` (`[Authorize(Roles = AutenticacaoService.PapelProfissional)]`, mesmo padrão de `AgendaController` — controller dedicado, DI de `ApplicationDbContext`/`VinculoService`). **O CRUD em si (criar, mudar status, excluir objetivo/combinado, alternar/adicionar/excluir combinado) não foi duplicado** — continua todo em `PacientesController.cs` e é reaproveitado sem nenhuma mudança, já que essas actions só validam `ProfissionalId`/`_vinculoService`, nunca dependem de uma tela específica.
- `Index()` (GET) carrega só os pacientes ativos do profissional (`_vinculoService.ObterPacientesAtivosAsync`, vira `List<PacienteSelectItemViewModel>` em `PlanosTratamentoViewModel.Pacientes`, usado tanto no `<select>` de filtro quanto no `<select>` de Paciente do modal "Novo Objetivo") e renderiza a view — a lista de objetivos em si **não** vem no SSR (view 100% orientada a AJAX, mesmo espírito da aba "Plano de Tratamento" de um paciente só).
- `Buscar(Guid? pacienteId, DateTime? dataInicio, DateTime? dataFim, string status = "todos")` (GET, JSON) — filtra `ObjetivosTerapeuticos` sempre por `ProfissionalId == User.ObterProfissionalId()` (nunca um Id vindo do cliente) mais os filtros opcionais (`status = "todos"` não filtra Status; qualquer outro valor faz `Enum.TryParse<StatusObjetivo>`); mesmo formato JSON de `PacientesController.ListarObjetivos`, acrescentando `pacienteId`/`pacienteNome`/`pacienteUrl` em cada item (a lista aqui é cross-paciente). `pacienteUrl` (`Url.Action` pra `Pacientes/Detalhes`) só é montado **depois** de `ToListAsync()` — `Url.Action` não é traduzível pra SQL, então a projeção materializa os campos simples primeiro e só depois monta a URL numa segunda passada em memória.
- `wwwroot/js/planos-tratamento.js` — adaptado de `plano-tratamento.js` (mesma renderização de card/combinados/progresso/histórico de sessões/popup "Visualizar Sessão", ver seção acima), mas: (1) sem `pacienteId` fixo — lê o estado dos filtros da toolbar (`change` nos `<select>`/inputs de data, botão "limpar período") e manda tudo pra `/PlanosTratamento/Buscar`; (2) cada card ganha um link `.ms-objetivo-card-paciente` (ícone `bi-person` + nome) acima do título, levando pra `Pacientes/Detalhes` do paciente daquele objetivo; (3) modal "Novo Objetivo" tem um `<select>` de Paciente obrigatório no lugar do `<input type="hidden">` fixo (`ObjetivoTerapeuticoViewModel.PacienteId` não precisou mudar, já era `[Required]`).
- Status do filtro usa os 4 valores reais do enum (`EmAndamento`/`Atingido`/`Pausado`/`Cancelado`) — rotulados como no resto do app ("Atingido", não "Concluído", pra manter o termo já estabelecido).
