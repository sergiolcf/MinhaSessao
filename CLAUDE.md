# MinhaSessao - Diretrizes do Projeto

## Visão Geral
Sistema de gestão de sessões de psicologia para Psicólogos e Pacientes.
Solução: SLCF_MinhaSessao.sln
Tech Stack: .NET 8 MVC, Entity Framework Core, PostgreSQL (Neon.tech), Bootstrap 5.

## Paleta de Cores & Layout
- Fundo Principal: Cinza Claro (#F8F9FA)
- Texto / Elementos Primários: Grafite (#2B2D42)
- Destaques / Botões de Ação: Laranja (#FF6B35)
- Layout: Limpo, acolhedor. Autenticação (Login/Cadastro) usa páginas dedicadas (`_LayoutAuth`), não modais; modais Bootstrap continuam usados dentro do Dashboard (ex.: cadastro de paciente, anotações).

## Comandos Principais
- Compilar Solução: dotnet build SLCF_MinhaSessao.sln
- Rodar localmente: dotnet run --project MinhaSessao.csproj
- Migrações EF Core: dotnet ef database update --project MinhaSessao.csproj

## Regras de Código
- Sempre mantenha os botões de confirmação/ação no canto inferior DIREITO dos modais.
- Um único formulário de login para ambos os perfis (identificação via DB) — hoje é a página `/Account/Login`, não mais um modal.
- Código e comentários em Português (PT-BR).
- Sempre validar alterações compilando a solução antes de finalizar tarefas.
- Toda action que lê/grava dados vinculados a um Profissional (Pacientes, Anotações, etc.) deve usar `[Authorize(Roles = AutenticacaoService.PapelProfissional)]` e obter o Id do profissional logado via `User.ObterProfissionalId()`; toda action exclusiva do Paciente usa `[Authorize(Roles = AutenticacaoService.PapelPaciente)]` e `User.ObterPacienteId()` — nunca confiar em um Id vindo de querystring, rota ou corpo da requisição para autorização.
- Operações de CRUD dentro do Dashboard (criar/editar/excluir/paginar/buscar) devem ser feitas via Fetch API (AJAX), sem recarregar a página inteira.

## Segurança & Dependências
- NUNCA instale pacotes NuGet, bibliotecas externas ou serviços de terceiros sem solicitar autorização prévia ao usuário.
- O projeto DEVE utilizar exclusivamente tecnologias e bibliotecas 100% gratuitas e open-source (sem custos de licença ou planos pagos).

## Arquitetura Implementada
Esta seção descreve o estado atual do projeto por módulo/domínio (não por card). Ao implementar um novo card que altera um módulo existente, atualize a seção correspondente em vez de adicionar uma seção nova.

### Estrutura de Models e Projeto
- Namespace raiz do projeto é `MinhaSessao` (não `SLCF_MinhaSessao` — este é só o nome do arquivo `.sln`).
- `Models/Entities/*` — entidades mapeadas pelo EF Core (`Id` como `Guid`, gerado via `Guid.NewGuid()`).
- `Models/ViewModels/*` — models de formulário/exibição, um por finalidade (criação, edição, listagem, detalhes).
- `Services/*` — lógica de domínio reutilizável (ex.: `AutenticacaoService`).
- `Extensions/*` — extension methods auxiliares (ex.: `ClaimsPrincipalExtensions`).
- `Helpers/*` — `ValidationAttribute` customizados de DataAnnotations reutilizáveis entre ViewModels (`MaiorDeIdadeAttribute`, `CpfValidoAttribute`, `ArquivoValidoAttribute`); os dois primeiros também implementam `IClientModelValidator` para ter validação client-side (ver "Cadastro (Profissional e Paciente)").
- Persistência via EF Core + PostgreSQL (`Npgsql.EntityFrameworkCore.PostgreSQL`, hospedado no Neon.tech), `Data/ApplicationDbContext.cs`. A connection string (`ConnectionStrings:DefaultConnection`) **nunca** fica em texto puro no repositório: `appsettings.json` mantém a chave vazia (`""`) só para documentar o nome esperado; o valor real vem de `dotnet user-secrets` em desenvolvimento local (`dotnet user-secrets set "ConnectionStrings:DefaultConnection" "..."`, guardado fora do repo) e da variável de ambiente `ConnectionStrings__DefaultConnection` no Render em produção (o `__` mapeia para `:` na configuração do ASP.NET Core).
- **`ApplicationDbContext.OnModelCreating` força `DateTimeKind.Utc` em todo `DateTime`/`DateTime?` do model** (via `ValueConverter` aplicado em loop sobre `modelBuilder.Model.GetEntityTypes()`, não campo a campo) — o Postgres mapeia `DateTime` como `timestamp with time zone`, que rejeita `Kind=Unspecified`/`Local` no `SaveChanges` (`System.ArgumentException: Cannot write DateTime with Kind=Unspecified...`); isso não existia no SQLite (não valida `Kind`) e pegou o cadastro de Paciente de surpresa (`DataNascimento` chegando `Unspecified` de um `<input type="date">`) logo após a migração para Postgres. Qualquer novo campo `DateTime` criado no futuro já herda essa conversão automaticamente, sem precisar lembrar de tratar `Kind` no controller.
- `Program.cs` roda `context.Database.Migrate()` logo após `builder.Build()` (dentro de um `try/catch` que só loga o erro, sem derrubar a aplicação) — aplica automaticamente as migrations pendentes e cria o schema no Postgres se ainda não existir, tanto local quanto no Render, sem precisar rodar `dotnet ef database update` manualmente a cada deploy.

### Autenticação (Cookie + Senha, Profissional e Paciente)
- Autenticação real por Cookie (`Program.cs`: `AddAuthentication().AddCookie()`, `LoginPath = /Account/Login`, expira em 7 dias com sliding expiration).
- Senha nunca é armazenada em texto puro: hash via `PasswordHasher<Profissional>`/`PasswordHasher<Paciente>` (`Microsoft.AspNetCore.Identity`, já incluso no SDK `Microsoft.NET.Sdk.Web`, sem pacote NuGet adicional).
- `Services/AutenticacaoService.cs` centraliza hash/verificação de senha (`HashSenha`/`VerificarSenha` para Profissional, `HashSenhaPaciente`/`VerificarSenhaPaciente` para Paciente) e a autenticação (`AutenticarProfissionalAsync`/`AutenticarPacienteAsync`, montam os Claims e chamam `SignInAsync`). Ambos os métodos de autenticação adicionam um Claim de papel (`ClaimTypes.Role`) com o valor de `AutenticacaoService.PapelProfissional` ou `PapelPaciente` — é isso que permite `[Authorize(Roles = "...")]` diferenciar as rotas de cada perfil.
- `Extensions/ClaimsPrincipalExtensions.cs`: `ObterProfissionalId()`/`ObterPacienteId()` extraem o Id do usuário logado a partir dos Claims — é assim que toda controller descobre "quem está logado" (cada uma só é chamada dentro de controllers já restritas ao papel correspondente).
- `Controllers/AccountController.cs`: `Login` (GET/POST) é o único formulário para os dois perfis — normaliza o e-mail com `.Trim().ToLower()`, procura primeiro em `Profissionais` e depois em `Pacientes`, autentica com o método correspondente e redireciona para `Dashboard` (Profissional) ou `PainelPaciente` (Paciente). `LoginSimuladoTeste` (atalho de desenvolvimento, loga automaticamente o primeiro profissional do banco) continua existindo na action; o botão "Entrar com Conta de Teste" em `Views/Account/Login.cshtml` só aparece quando `ASPNETCORE_ENVIRONMENT=Development` (flag local `exibirLoginContaTeste = Env.IsDevelopment()`, via `@inject IWebHostEnvironment Env` na própria View — não há como a aplicação publicada saber de qual branch do Git ela veio, então quem decide é a variável de ambiente do serviço de hospedagem, não o código). Localmente já roda como Development por padrão (`Properties/launchSettings.json`); no Render, configure `ASPNETCORE_ENVIRONMENT=Development` só no serviço que publica a branch Develop — no serviço de Produção (branch main), não defina essa variável (o padrão do Render já é Production) ou defina-a explicitamente como Production. `Logout` (comum aos dois perfis).
- Views: `Views/Account/Login.cshtml` e `Views/Account/Cadastro.cshtml`, ambas com `Views/Shared/_LayoutAuth.cshtml` (layout minimalista, não usa o `_Layout.cshtml` público nem os layouts de dashboard).
- Ainda não implementado: troca de senha obrigatória no primeiro login e recuperação de senha. O Paciente pode ganhar acesso tanto pelo cadastro feito pelo Profissional (senha temporária, ver "Pacientes" abaixo) quanto por autocadastro próprio (ver "Cadastro (Profissional e Paciente)" abaixo).

### Cadastro (Profissional e Paciente)
- Tela única `Views/Account/Cadastro.cshtml` (`_LayoutAuth`), com abas Bootstrap ("Sou Profissional" / "Sou Paciente") — substituiu o antigo modal de cadastro do Profissional na landing page e a rota solta `/Paciente/Cadastrar`. Cada aba é um `<form>` independente que posta para uma action diferente do `AccountController`; os campos usam nomes simples (`NomeCompleto`, `Email`, `Senha`...), sem prefixo `Model.Profissional.X`/`Model.Paciente.X`, porque cada action recebe seu próprio ViewModel (`ProfissionalViewModel`/`PacienteCadastroViewModel`) direto como parâmetro — os campos de cada aba vêm de um `<partial>` próprio (`_CamposCadastroProfissional.cshtml`/`_CamposCadastroPaciente.cshtml`) com `@model` do tipo específico, exatamente para gerar esses nomes sem prefixo.
- `Models/ViewModels/CadastroViewModel.cs` só existe para renderizar a tela (`PerfilAtivo` + os dois sub-ViewModels vazios ou repopulados após erro) — nunca é o tipo postado por um form.
- `Controllers/AccountController.cs`:
  - `[HttpGet] Cadastro(string? perfil)` — monta a tela; `PerfilAtivo` vem da querystring (`?perfil=paciente`), default `"profissional"`.
  - `[HttpPost] CadastroProfissional(ProfissionalViewModel model)` — mesma lógica que existia em `ProfissionalController.Criar` (upload de foto opcional para `wwwroot/uploads/profissionais/`, hash da senha, autologin), mas retornando `View`/`RedirectToAction` em vez de `Json` (form MVC tradicional, mesmo padrão do `Login`). Sucesso → `RedirectToAction("Index", "Dashboard")`, direto, sem modal de sucesso.
  - `[HttpPost] CadastroPaciente(PacienteCadastroViewModel model)` — mesma lógica que existia em `PacienteController.Cadastrar` (checagem de e-mail duplicado, hash da senha, autologin). Sucesso → `RedirectToAction("Index", "PainelPaciente")`. **Não cria nenhum `VinculoPacienteProfissional`** — vínculo continua sendo criado só pelo Profissional (ver "Pacientes"/"Vínculo Paciente-Profissional"). Antes de gravar, `Telefone` é normalizado inline (`new string(model.Telefone.Where(char.IsDigit).ToArray())`, mesmo espírito de `CpfUtil.Normalizar` mas sem reaproveitar essa classe — o nome é específico de CPF) — `Cpf` já era normalizado via `CpfUtil.Normalizar`. Assim, ambos os campos são salvos só com dígitos, independente da máscara aplicada no front-end.
  - Em erro (validação ou e-mail duplicado), cada action re-renderiza `View("Cadastro", ...)` com `PerfilAtivo` na aba correta e os dados já digitados preservados.
- `wwwroot/js/cadastro.js` — contador de caracteres da Apresentação do Profissional (migrado do antigo `site.js`); as máscaras de `#Cpf`/`#Telefone` (aba Paciente) e `#RegistroCRP`/`#Telefone` (aba Profissional, `00/000000` e fixo/celular dinâmico) — vanilla JS puro (sem lib nova), função `aplicarMascara` reformata o `value` do input nos eventos `input`/`blur`/`change` (não só `input`: alguns fluxos de autopreenchimento do navegador podem preencher o campo sem disparar um `input` "de verdade", então a máscara ficava sem aplicar — reportado em teste manual do usuário) e também reformata uma vez de cara caso o campo já chegue preenchido. **Toda busca de campo é escopada a `#tab-paciente`/`#tab-profissional`** (`querySelector`, nunca `getElementById` puro) — `Telefone` existe nos dois formulários da mesma página (`Cadastro.cshtml` renderiza as duas abas no DOM, só uma fica visível), então `getElementById("Telefone")` sempre pegava o primeiro do documento (Profissional) e deixava o outro sem máscara; **e** os adaptadores do jQuery Validate Unobtrusive (`maiordeidade`/`cpfvalido`, registrados fora do `DOMContentLoaded` para rodar antes do unobtrusive escanear o formulário) que dão vida client-side aos `ValidationAttribute` customizados que implementam `IClientModelValidator` — sem isso, um `ValidationAttribute` customizado só é checado no POST (servidor), nunca ao digitar/perder foco, diferente de `[Required]`/`[RegularExpression]`/etc, que já têm suporte nativo do ASP.NET Core; `configurarValidacaoFoto()` faz uma checagem equivalente (tamanho/extensão) para o input de arquivo `#Foto`, fora do jQuery Validate (File API não tem adaptador unobtrusive pronto), limpando o input e escrevendo direto no `data-valmsg-for="Foto"` quando inválido; **e** `configurarToggleSenha()`, um botão próprio de mostrar/ocultar senha (`.ms-toggle-senha`, ícone `bi-eye`/`bi-eye-slash` dentro de um `input-group` ao lado de cada campo Senha/ConfirmarSenha, nos dois formulários) — existe porque o ícone nativo de revelar senha do navegador (Edge, alguns gerenciadores de senha) aparece de forma inconsistente entre campos/navegadores e não dá pra controlar via CSS/JS; o nativo do Edge é escondido via `::-ms-reveal`/`::-ms-clear` em `auth.css` para não duplicar com o nosso ícone.
- **Validação de `PacienteCadastroViewModel`** (autocadastro de Paciente, `Views/Account/_CamposCadastroPaciente.cshtml`): `NomeCompleto` exige `[StringLength(3, 100)]` + `[RegularExpression]` (só letras/acentos, com espaço — força nome e sobrenome); `Telefone` usa `[RegularExpression]` aceitando tanto o valor já mascarado pelo JS quanto dígitos puros (fallback caso o JS não rode), garantindo 10/11 dígitos; `Cpf` usa `[RegularExpression]` (formato/quantidade de dígitos) **e** `[CpfValido]` (`Helpers/CpfValidoAttribute.cs` — dígito verificador pelo algoritmo oficial da Receita Federal, rejeita também CPF com todos os dígitos iguais tipo `111.111.111-11`; um CPF só com formato correto mas dígito verificador errado, ex. `147.147.144-78`, passava batido antes dessa validação existir); `DataNascimento` usa `[MaiorDeIdade(18)]` (`Helpers/MaiorDeIdadeAttribute.cs` — calcula idade a partir de `DateTime.UtcNow.Date`, reutilizável em qualquer ViewModel com campo de data de nascimento); `Senha` exige `[MinLength(8)]` + `[RegularExpression]` (1 maiúscula, 1 número, 1 caractere especial). `MaiorDeIdadeAttribute` e `CpfValidoAttribute` implementam `IClientModelValidator` (gerando `data-val-maiordeidade`/`data-val-cpfvalido` nos inputs) justamente para terem validação ao vivo igual aos atributos nativos — ver `cadastro.js` acima. Essas regras são específicas do autocadastro — `Models/ViewModels/PacienteViewModel.cs` (cadastro de Paciente feito pelo Profissional, `PacientesController.Criar`) **não** foi alterado, continua só com `[Required]`/`[EmailAddress]` simples.
- **Validação de `ProfissionalViewModel`** (`Views/Account/_CamposCadastroProfissional.cshtml`): `NomeCompleto` exige `[StringLength(3, 100)]` + `[RegularExpression]` (nome e sobrenome, mesma regra do Paciente); `RegistroCRP` usa `[RegularExpression]` no formato `00/000000` (2 dígitos + `/` + 6 dígitos); `Telefone` usa a mesma `[RegularExpression]` fixo/celular do Paciente; `Senha` exige `[MinLength(8)]` + `[RegularExpression]` (1 maiúscula, 1 número, 1 caractere especial — antes só pedia 6 caracteres, sem mais regra nenhuma); `Apresentacao` passou de opcional (`string?`, só `[StringLength(500)]`) para obrigatória (`string`, `[Required]` + `[StringLength(500, MinimumLength = 30)]`) — só afeta o autocadastro, `AtualizarPerfilProfissionalViewModel` (tela Configurações) é um ViewModel separado e continua sem exigir tamanho mínimo; `Foto` (`IFormFile?`, continua opcional) ganhou `[ArquivoValido]` (`Helpers/ArquivoValidoAttribute.cs` — máximo 2MB, extensões `.jpg`/`.jpeg`/`.png`; sobrescreve o overload `IsValid(object, ValidationContext)` em vez de mutar `ErrorMessage` em `IsValid(object)`, para não compartilhar estado entre requisições concorrentes na mesma instância cacheada do atributo — mensagem final distingue "tamanho" de "extensão inválida", por isso não implementa `IClientModelValidator`/`data-val-*`; o equivalente client-side é o `configurarValidacaoFoto()` do `cadastro.js`, feito com a File API direto, não via jQuery Validate).

### Pacientes
- `Controllers/PacientesController.cs`: `Index` (lista os pacientes vinculados ao profissional logado), `Detalhes` (ficha do paciente), `VerificarPacienteExistente`, `Vincular`, `Criar`, `GerarNovaSenha`.
- Toda consulta/gravação revalida a posse via `VinculoService` (ver seção "Vínculo Paciente-Profissional" abaixo) — **nunca** compara um `ProfissionalId` direto na entidade `Paciente` (ela não tem mais esse campo).
- **Fluxo "Novo Paciente" em 2 passos** (modal `#modalCadastroPaciente` em `Views/Pacientes/Index.cshtml`, controlado por `wwwroot/js/pacientes.js`), pra não duplicar paciente que já existe — **o CPF é o identificador usado pra buscar/evitar duplicidade** (o e-mail é só um campo cadastral comum, não é mais usado nessa checagem):
  1. Etapa "Verificar CPF" — só um campo de CPF (obrigatório, com máscara `000.000.000-00` aplicada em JS puro, sem lib nova); `[HttpGet] VerificarPacienteExistente(cpf)` busca via `BuscarPacientePorCpfAsync` (método privado, normaliza removendo tudo que não for dígito com `CpfUtil.Normalizar`, reaproveitado por `Criar`) e retorna `{ existe, pacienteId, nomeCompleto, iniciais }`.
  2. Se `existe: true` → etapa "Paciente encontrado" (mostra iniciais/nome, sem reexibir nem sobrescrever os dados dele). Botão "Vincular este paciente" chama `[HttpPost] Vincular(pacienteId)`, que confere se já está vinculado (erro "Este paciente já está na sua lista.") e senão chama `VinculoService.CriarVinculo` — **não** gera senha nova nem mexe no cadastro do paciente.
  3. Se `existe: false` → etapa "Cadastro completo" (formulário de sempre, CPF já vem preenchido e `readonly`, com um link "trocar CPF" pra voltar à etapa 1; e-mail volta a ser um campo normal e obrigatório do formulário). Submete pro `[HttpPost] Criar` de sempre.
  - `Criar` continua existindo exatamente como antes (gera senha temporária, cria o Vínculo), mas a checagem de duplicidade por CPF no envio final passou a ser só uma **rede de segurança contra condição de corrida** — não deveria ocorrer no fluxo normal (a tela já checou o CPF na etapa 1); se ocorrer, `Criar` **não cadastra** e retorna erro pedindo pra verificar de novo (sem vincular automaticamente).
  - O modal sempre volta pra etapa 1 ao reabrir (`show.bs.modal` reseta tudo).
  - `Models/ViewModels/CpfUtil.cs` centraliza a normalização de CPF (remove tudo que não for dígito) — usado tanto por `PacientesController` quanto por `AccountController.CadastroPaciente`, pra garantir que o CPF é sempre armazenado só com dígitos, e as buscas funcionam independente de como foi digitado.
  - CPF é obrigatório em todo cadastro de Paciente (`PacienteViewModel.Cpf` e `PacienteCadastroViewModel.Cpf` com `[Required]`) — tanto no cadastro feito pelo Profissional quanto no autocadastro.
- Acesso do paciente: ao cadastrar do zero, `Criar` gera uma senha temporária aleatória (`AutenticacaoService.GerarSenhaTemporaria`), salva só o hash (`HashSenhaPaciente`) e retorna o texto puro **uma única vez** no JSON de sucesso. O front-end (`wwwroot/js/pacientes.js` + modal compartilhada `#modalSenhaTemporaria` em `_LayoutDashboard.cshtml`, via `window.exibirSenhaTemporaria`) exibe essa senha com um botão de copiar (`navigator.clipboard`) — ela nunca é armazenada em texto puro nem pode ser recuperada depois.
- Se a senha for perdida, o profissional usa o botão "Gerar nova senha" na aba Dados Cadastrais da ficha (`wwwroot/js/pacientes-detalhes.js`, action `GerarNovaSenha`), que sobrescreve o hash antigo (invalidando-o) e mostra a nova senha do mesmo jeito. Não existe fluxo de "recuperar" a senha antiga — só resetar.
- O paciente já consegue logar com essa senha em `/Account/Login` (login continua sendo por e-mail, ver seção "Autenticação" acima) e cai no seu próprio painel — ver "Painel do Paciente" abaixo. Além disso, o próprio paciente pode se autocadastrar direto — ver "Cadastro (Profissional e Paciente)" acima; `Models/ViewModels/PacienteCadastroViewModel.cs` só pede os campos essenciais (`NomeCompleto`, `Email`, `Telefone`, `DataNascimento`, `Cpf`, `Senha`/`ConfirmarSenha`) — `Sexo`, `ContatoEmergencia` e `Profissao` ficam de fora, o paciente completa depois em Configurações (ainda não implementado).

### Vínculo Paciente-Profissional
- Relação N:N via `Models/Entities/VinculoPacienteProfissional.cs` (`PacienteId`, `ProfissionalId`, `Status` — enum `StatusVinculo.Ativo`/`Encerrado`, `DataInicio`, `DataFim`) — substituiu a antiga FK direta `Paciente.ProfissionalId` (removida), permitindo que um paciente tenha vários profissionais ao longo do tempo.
- `Services/VinculoService.cs` (registrado no DI como scoped) centraliza toda a checagem de posse e criação de vínculo: `PacientePertenceAoProfissionalAsync(pacienteId, profissionalId)` (só considera vínculo com `Status = Ativo`), `ObterPacientesAtivosAsync(profissionalId)` (lista para o `Index`) e `CriarVinculo(pacienteId, profissionalId)` (usado por `PacientesController.Criar`; não chama `SaveChangesAsync` sozinho — quem chama inclui na mesma unidade de trabalho que grava o `Paciente`).

- Migration `AddVinculoPacienteProfissional`: cria a tabela `Vinculos` **antes** de mexer em `Pacientes`, faz um `INSERT ... SELECT` migrando cada paciente existente para um vínculo `Ativo` (com a `DataCadastro` do paciente como `DataInicio`) e só depois remove a FK/coluna antiga — a ordem importa, senão os dados são perdidos antes de serem copiados.
- Ainda não existe tela de gerenciar vínculos (ex.: encerrar vínculo com um paciente) — fica para um card futuro.

### Sessões (Painel do Profissional)
- Tela própria `Controllers/SessoesController.cs` (`[Authorize(Roles = AutenticacaoService.PapelProfissional)]`) + `Views/Sessoes/Index.cshtml` (layout `_LayoutDashboard`) — controller dedicado, mesmo padrão de `PacientesController` (não fica dentro do `DashboardController`), com DI de `ApplicationDbContext`, `ILogger<SessoesController>` e `VinculoService`.
- **Paginação (10 por página) + rolagem interna (~4 linhas visíveis)**, mesma regra usada nas Anotações Confidenciais: `SessoesController.ObterPaginaSessoesAsync` (privado, reaproveitado por `Index` e `BuscarSessoes`) pagina 10 sessões por vez, filtrando por `aba` (`"agendadas"` = `Status = Agendada` ordenado por `DataHora` crescente; `"historico"` = `Status != Agendada` ordenado decrescente) e, opcionalmente, por `pacienteId`. O `Index()` (GET) só busca a página 1 de cada aba (evita carregar todas as sessões do profissional de uma vez); `BuscarSessoes(string aba, int pagina, Guid? pacienteId)` (GET, JSON) é o endpoint AJAX chamado pela troca de página, pela troca de aba (a aba "Histórico" só é buscada na primeira vez que é aberta — `wwwroot/js/sessoes.js`, flag `ms_historicoCarregado`) e pelo filtro de paciente. Na View, cada tabela fica dentro de `.table-responsive.ms-dash-table-scroll` (`max-height` + `overflow-y: auto` + `thead` `position: sticky`, `dashboard.css`) e a paginação usa a classe compartilhada `.ms-pagination` (generalizada a partir do que antes era só `#paginacaoAnotacoes`, também usada em `Views/Pacientes/Detalhes.cshtml`).

Botão "X" (`#btnLimparFiltroPacienteSessoes`) limpa a seleção. Estilos próprios `.ms-filtro-paciente-*` em `dashboard.css` (reaproveita só o wrapper `.ms-anotacao-toolbar`/`.ms-anotacao-search` para o ícone de funil).

- **Campo Paciente do modal "Nova Sessão" — lookup, não mais `<select>`**: `#NovaSessaoPacienteBusca` (texto) + `#NovaSessaoPacienteId` (hidden, é o que é postado como `PacienteId`) reaproveitam exatamente a mesma UX/endpoint do filtro acima (`BuscarPacientesFiltro`, sugestões em `#sugestoesNovaSessaoPaciente`, mesmas classes `.ms-filtro-paciente-*`). ### Agenda (Painel do Profissional) — V0
- Tela própria `Controllers/AgendaController.cs` (`[Authorize(Roles = AutenticacaoService.PapelProfissional)]`) + `Views/Agenda/Index.cshtml` (layout `_LayoutDashboard`) — controller dedicado, mesmo padrão de `SessoesController`/`PacientesController` (não fica dentro do `DashboardController`).
- **Grade semanal/mensal é implementada em HTML/CSS/JS puro (`wwwroot/js/agenda.js`) — não usa nenhuma biblioteca de calendário (ex.: FullCalendar)**, para não introduzir uma dependência externa nova; a "grade de rastreabilidade visual" é uma grid CSS de 7 colunas (semana, `.ms-agenda-grade-semana`) ou 7 colunas x N semanas (mês, `.ms-agenda-grade-mes`, incluindo dias de padding do mês anterior/seguinte para fechar semanas completas), com um botão `.ms-agenda-chip` por sessão dentro de cada dia. Alternar entre as visões (`#btnAgendaVisaoSemana`/`#btnAgendaVisaoMes`) e navegar (`#btnAgendaAnterior`/`#btnAgendaProximo`/`#btnAgendaHoje`) só troca a data de referência (`ms_agendaReferencia`, em memória no JS) e busca de novo — não há estado persistido entre navegações de página.
- `AgendaController.Index()` (GET) monta `PainelAgendaProfissionalViewModel` (`Models/ViewModels/PainelAgendaProfissionalViewModel.cs`) com só os 3 contadores dos cards do topo — a grade em si **não** vem do SSR, é buscada pelo JS assim que a página carrega (`carregarAgenda()` no final de `agenda.js`), evitando duplicar a lógica de montagem de chip em Razor e em JS (diferente do padrão SSR+AJAX usado em `Sessões`, aqui simplificado de propósito por ser uma V0).
  - `SessoesSemana`: **janela móvel dos últimos 7 dias** (`hoje.AddDays(-6)` até `hoje`, não a semana de calendário que aparece na grade, que o profissional navega livremente) — conta só `Agendada`/`Realizada` (`Cancelada` não ocupa agenda de fato).
  - `SessoesMes`: contagem de **todas** as sessões (qualquer `Status`) com `DataHora` no mês corrente — é o volume total; o card "Sessões Canceladas" ao lado é o recorte específico de cancelamentos, não uma subtração do total.
  - `SessoesCanceladasMes`: `Status == Cancelada` no mês corrente.
- `BuscarSessoesAgenda(DateTime inicio, DateTime fim)` (GET, JSON) — único endpoint de dados da grade, filtra sempre por `ProfissionalId == User.ObterProfissionalId()` e por `DataHora >= inicio && DataHora < fim` (intervalo half-open); é o mesmo endpoint pras duas visões — quem calcula o intervalo certo (incluindo os dias de padding do mês) é o cliente (`agenda.js`, `inicioGradeMes`/`fimGradeMesExclusivo` vs. `inicioDaSemana`).
- Cores dos `.ms-agenda-chip`/`.ms-agenda-dot` (Agendada azul, Realizada verde, Cancelada cinza) são **classes próprias da Agenda**, não os badges `.ms-badge-agendada/realizada/cancelada` já usados em Sessões/Ficha do Paciente (que são laranja/verde/vermelho) — foi um pedido explícito para esta tela especificamente; a modal de detalhes (`#modalDetalhesSessaoAgenda`), por outro lado, reaproveita os badges `.ms-badge-*` de sempre, então a mesma sessão pode aparecer com uma cor na grade e outra na modal — intencional, não inconsistência a corrigir.
- Clicar num `.ms-agenda-chip` abre a modal `#modalDetalhesSessaoAgenda` (Paciente/Data e Hora/Duração/Status + botão "Acessar Prontuário" para `/Pacientes/Detalhes/{pacienteId}`) preenchida direto pelos `data-*` do botão — sem round-trip ao servidor, mesmo padrão já usado em `sessoes.js` para o clique numa linha da tabela.
- Item "Minha Agenda" do menu lateral do Profissional (`Views/Shared/_LayoutDashboard.cshtml`) aponta para `asp-controller="Agenda" asp-action="Index"` (antes era um link `href="#"` estático).
- **Criar sessão a partir de um dia da grade**: clicar num dia (fora de um `.ms-agenda-chip`, que abre a modal de detalhes) abre a modal "Nova Sessão" **direto na própria tela da Agenda**, sem navegar para "Minhas Sessões" — `agenda.js` chama `window.MsNovaSessao.abrirComData(dataIso)`, que preenche o campo Data e mostra a modal (a Hora fica em aberto, para o profissional escolher). Editar uma sessão existente pela Agenda continua sendo só leitura (modal de detalhes com link "Acessar Prontuário") — a edição de fato só existe em "Minhas Sessões".
- **A modal "Nova Sessão" é compartilhada entre "Minhas Sessões" e "Minha Agenda"**, não duplicada: `Views/Shared/_ModalNovaSessao.cshtml` (parâmetro `Models/ViewModels/NovaSessaoModalViewModel.cs` — só `Pacientes`/`DuracaoPadraoSessaoMinutos`) contém o HTML da modal "Nova Sessão" **e** da popup "Procurar Paciente"; `wwwroot/js/nova-sessao.js` contém toda a lógica (lookup de paciente, seletor de hora, submit pro `/Sessoes/Criar`, toast próprio `#toastNovaSessao`) e expõe `window.MsNovaSessao.abrirComData(dataIso)` pra quem precisar abrir a modal já preenchida sem round-trip. Tanto `Views/Sessoes/Index.cshtml` quanto `Views/Agenda/Index.cshtml` incluem a partial e carregam os scripts nesta ordem: `sessao-utils.js` → `nova-sessao.js` → o script da própria página (`sessoes.js`/`agenda.js`) — a ordem importa porque `nova-sessao.js` usa os helpers globais de `sessao-utils.js` (`combinarDataHora`, `separarDataHora`, `configurarSeletorHora`, `escaparHtml`, antes definidos dentro de `sessoes.js`) e `agenda.js` usa `window.MsNovaSessao`, que só existe depois que `nova-sessao.js` roda. **Se o formulário da Nova Sessão mudar (novo campo, validação etc.), mexer só na partial/`nova-sessao.js` — nunca duplicar de volta pra `Sessoes/Index.cshtml` ou `Agenda/Index.cshtml`.** Após criar com sucesso, a modal recarrega a página atual (`window.location.reload()`) — funciona igual nas duas telas, sem precisar saber em qual delas está.
- `AgendaController` também injeta `VinculoService` (igual `SessoesController`) só pra montar `Pacientes`/`DuracaoPadraoSessaoMinutos` do `PainelAgendaProfissionalViewModel`, usados exclusivamente pela partial `_ModalNovaSessao` — a grade em si não depende dessa lista.

### Plano de Tratamento (dentro da Ficha do Paciente)
- Substituiu o placeholder ("Conteúdo em construção...") deixado no CARD-16 pela aba real de objetivos terapêuticos. **Já existiu uma tentativa anterior desse mesmo desenho dentro do próprio CARD-16** (migrations `AdicionaObjetivosECombinados` → `AjustaArquiteturaCombinados` → `RemoveObjetivosECombinados`, todas revertidas antes daquele merge) — a implementação atual (CARD-17) foi refeita do zero a partir de uma análise de produto validada com o usuário (status aprovados, modal "tudo em uma tela", cards com barra de progresso).
- Entidades `Models/Entities/ObjetivoTerapeutico.cs` (`PacienteId`, `ProfissionalId` — quem criou —, `Titulo`, `Descricao?`, `Status`, `DataCriacao`, `DataAtualizacao?`) e `Models/Entities/Combinado.cs` (`ObjetivoTerapeuticoId`, `Descricao`, `Concluido`, `DataCriacao`), 1:N. `Models/Entities/StatusObjetivo.cs` (enum `EmAndamento`/`Atingido`/`Pausado`/`Cancelado`).
- `ApplicationDbContext` ganhou o primeiro `OnModelCreating` do projeto (até então não existia Fluent API nenhuma) só para configurar essas duas relações: `ObjetivoTerapeutico` → `Paciente`/`Profissional` obrigatórios com `DeleteBehavior.Restrict` (não apaga objetivos se o cadastro pai for removido) e `Combinado` → `ObjetivoTerapeutico` obrigatório com `DeleteBehavior.Cascade` (apagar o objetivo apaga os combinados junto). Migration `AddPlanoTratamento`.
- CRUD completo via AJAX em `PacientesController.cs`, mesmo padrão de `AnotacaoConfidencial` (uso de `_vinculoService.PacientePertenceAoProfissionalAsync`/`User.ObterProfissionalId()`, try/catch com `_logger.LogError`, retorno `Json`): `ListarObjetivos` (GET, por paciente, com combinados aninhados e contadores `totalCombinados`/`combinadosConcluidos`), `SalvarObjetivo` (POST — cria o objetivo e os combinados da lista no mesmo `SaveChangesAsync`, via navegação `objetivo.Combinados`; ignora combinados em branco), `AtualizarStatusObjetivo`, `ExcluirObjetivo` (cascade cuida dos combinados), `AlternarCombinado`, `AdicionarCombinado` e `ExcluirCombinado` (esses três de combinado avulso validam o dono via o `ObjetivoTerapeutico` pai, não existe checagem direta de "combinado pertence ao profissional"). `Models/ViewModels/ObjetivoTerapeuticoViewModel.cs` é só para criação (objetivo + `List<string> Combinados` juntos, Proposta A "tudo em uma tela") — não existe ViewModel de edição de combinado avulso.
- View 100% orientada a AJAX (sem SSR da lista, diferente do padrão usado em Anotações/Sessões — simplificação deliberada, mesmo espírito da Agenda V0): `Views/Pacientes/Detalhes.cshtml` só renderiza o container `#objetivosContainer`/`#listaObjetivos` vazio (com empty state) e a modal `#modalNovoObjetivo`; `wwwroot/js/plano-tratamento.js` (IIFE própria, sem interferir com `anotacoes.js`) chama `ListarObjetivos` assim que a página carrega e renderiza os cards.
- Card por objetivo: título + badge de status (`bg-info` Em Andamento, `bg-success` Atingido, `bg-warning text-dark` Pausado — o projeto usa Bootstrap 5.1, que não tem o utilitário `text-bg-*` do 5.3, por isso o `text-dark` manual pro contraste no amarelo —, `bg-secondary` Cancelado), progress bar Bootstrap nativa (`combinadosConcluidos`/`totalCombinados`), lista de combinados com checkbox (chama `AlternarCombinado` no `change`) e um `<select>` de status (chama `AtualizarStatusObjetivo` no `change`) — os dois recarregam a lista inteira do servidor após a chamada (fonte da verdade fica no backend, sem estado otimista complexo no JS).
- **Histórico de Sessões** (dentro do card, abaixo da lista de combinados), carregado sob demanda e paginado — não vem junto do `ListarObjetivos` inicial, pra não pesar a tela quando um objetivo acumula muitas sessões: `ObjetivoTerapeutico` ganhou a navegação `ICollection<SessaoObjetivo> SessoesObjetivo` (configurada em `ApplicationDbContext.OnModelCreating` via `WithMany(o => o.SessoesObjetivo)` no relacionamento `SessaoObjetivo`→`ObjetivoTerapeutico` já existente — mesma FK/coluna de antes, só nomeando a navegação inversa, por isso não precisou de migration nova). `PacientesController.ListarObjetivos` expõe só a contagem `totalSessoesVinculadas = o.SessoesObjetivo.Count` de cada objetivo; a lista de sessões em si vem de `ListarSessoesDoObjetivo(Guid objetivoId, int pagina = 1)` (GET, paginação fixa de 10, valida o dono comparando `ObjetivoTerapeutico.ProfissionalId` direto — mesmo padrão simplificado de `AtualizarStatusObjetivo`/`ExcluirObjetivo`, sem precisar do `VinculoService` porque o objetivo já guarda o `ProfissionalId` de quem criou —, retorna `{ success, sessoes: [{ dataHora, observacao }], paginaAtual, totalPaginas }` ordenado por `Sessao.DataHora` decrescente). Em `plano-tratamento.js`, `criarCardObjetivo` renderiza um link "Histórico de Sessões (N)" (`data-bs-toggle="collapse"`, mesmo padrão da "Evolução da Sessão" em `Pacientes/Detalhes.cshtml`) sobre uma `.collapse` vazia (`data-carregado="false"`); o listener `show.bs.collapse` em `listaObjetivos` (delegado, dispara na primeira expansão de cada card) chama `carregarHistoricoSessoes(collapseEl, 1)`, que busca a página e marca `data-carregado="true"` — expansões seguintes não buscam de novo. Um botão "Carregar mais" dentro da própria `.collapse` (escondido quando `paginaAtual >= totalPaginas`) busca a próxima página e faz *append* na lista (`insertAdjacentHTML("beforeend", ...)`), sem substituir os itens já carregados. Sem nenhuma sessão vinculada (`totalSessoesVinculadas === 0`), o card mostra só o texto "Nenhuma sessão registrada ainda" (sem link nem `.collapse`). Como `carregarObjetivos()` reconstrói todos os cards do zero a cada ação (criar/excluir objetivo, alternar combinado, mudar status), o histórico expandido sempre volta a fechado/não carregado depois de qualquer uma dessas ações — comportamento aceito, não é bug. Estilos `ms-objetivo-historico-*` em `dashboard.css`.
- O envio da modal "Novo Objetivo" usa `FormData`/campos de formulário (nunca JSON) — é o que faz o `[ValidateAntiForgeryToken]` e o model binding do `List<string> Combinados` funcionarem (o MVC lê o token e monta a lista a partir de múltiplos campos `Combinados` com o mesmo nome; um `fetch` com `Content-Type: application/json` quebraria os dois).
- Estilos próprios `ms-objetivo-*`/`ms-combinado-*` em `dashboard.css`, reaproveitando `ms-dash-card`/`ms-dash-empty-state`/`ms-dash-page-header`/`ms-required`/`ms-alert-erro` já existentes.
- Fica para um card futuro: edição de título/descrição de um objetivo já criado (hoje só criação, mudança de status e exclusão) e alguma tela de histórico/filtro caso o volume de objetivos por paciente cresça.
